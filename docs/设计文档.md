## 1. 赛题要点与目标对齐

赛题要求实现自动化 AI 安全知识情报系统，具备三大核心能力：**情报监测**、**情报富化**、**情报问答**，并同步构建 AI 安全论文 / 技术标准 / 政策法规知识底座。赛题为半开放，明确要求"基于智能体技术"，评价重点落在 Agent 自主决策与任务编排、跨文档关联推理、以及从采集到问答的全流程自动化。

## 2. 范围取舍（砍什么 / 保什么）

| 项 | 决定 | 理由 |
|---|---|---|
| 数据源 | **4 类**：NVD/CVE API、GitHub Advisory(GHSA + webhook)、arXiv(论文)、安全社区 RSS | 合格线 3 类；4 类留余量；能稳定跑通 > 数量 |
| 富化维度 | **4 维** | 合格线 3 维，4 维留余量 |
| 图数据库 | **不引入 Neo4j**，用 PostgreSQL 边表 + 递归 CTE 实现 2~3 跳 | 省 3~4 人日与一个运维组件 |
| 搜索引擎 | **不引入 ES**，pgvector + PG 全文/模糊 + RRF 融合 | 省 2 人日与一个运维组件 |
| Agent | **3 角色 + Supervisor**（Triage / Enrich / QA） | 赛题核心（15 分）必须做，角色数不必多 |
| 模型 | 主力 `deepseek-v4-flash`，富化推理与问答推理链路由到 `deepseek-v4-pro`，本地 Ollama 兜底 | 成本可控 + 降级路径即答辩素材 |
| 存储 | PostgreSQL + pgvector + Redis（原文先落本地目录，MinIO 可选） | 组件越少越好部署 |
| 前端 | **3 页**：态势大屏 / 漏洞详情（含证据链）/ 问答 | 时间紧，不做花哨动画 |

明确砍掉（若进度提前再捡）：厂商公告适配器、ExploitDB 抓取器、内部资产库对接、图可视化大屏、用户画像个性化推荐、Neo4j 图数据库。

## 5. 数据模型

### 5.1 PostgreSQL 核心表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `raw_item` | source, external_id, url, title, content_text, published_at, fetched_at, etag, content_hash, simhash, raw_json | 原始情报落地，带采集时间戳（时效指标） |
| `vuln` | cve_id, ghsa_id, title, description, cvss_vector, cvss_score, severity, cwe[], cpe[], epss, kev, ai_risk_category, exploit_status | 漏洞主表（去重合并后）。**F 线需追加**：`references`(JSON)、`affected_products`(JSON)、`version_ranges`(JSON)、`quality_score`(Float) |
| `vuln_source` | vuln_id, raw_item_id, source | 多源关联，支撑交叉验证与合并率统计 |
| `enrichment` | vuln_id, dimension, value_json, evidence_json, confidence, model, agent, version, created_at | **富化统一表**：证据链、准确率统计、字段级评测全部基于它 |
| `asset` / `asset_vuln` | product, cpe, vendor, exposure, org | 受影响资产（本期只做 NVD CPE + 厂商产品抽取） |
| `paper` / `vuln_paper` | arxiv_id, doi, title, abstract, year, relation_type | 论文及其与漏洞的关联 |
| `poc` | vuln_id, url, repo, kind(exploit/patch), language, stars, verified | POC 验证代码 |
| `ttp_mapping` | vuln_id, tactic, technique_id | MITRE ATT&CK 映射 |
| `policy_standard` | type, issuer, title, url, effective_date | 政策法规与技术标准 |
| `chunk` / `embedding` | owner_type, owner_id, chunk_no, content, embedding vector(1024) | 检索单元，多态关联 vuln/paper/policy |
| `graph_edge` | src_type, src_id, rel, dst_type, dst_id, props | **关系边表**，替代图数据库，支撑多跳 |
| `agent_run` / `agent_step` | run_id, agent, node, state, input, output, tokens, cost, latency, error | Agent 执行轨迹（演示与可观测） |
| `alert` | level, vuln_id, message, delivered, acked | 告警记录 |
| `eval_case` / `eval_result` | kind, question, expected, answer, score, judge | 评测集与结果 |
| `sync_watermark` | source, last_full_sync, last_item_ts, etag | 增量同步游标 |
| `source_config` | source, enabled, priority, rate_limit, extra | 数据源开关与限速 |

### 5.2 关系图（边表表达）

```
(Vuln)─[AFFECTS]→(Product)─[MADE_BY]→(Vendor)
(Vuln)─[COMPONENT_OF]→(Project)          # Ollama / vLLM / Triton 等 AI 框架
(Vuln)─[HAS_POC]→(POC)─[ON_REPO]→(Repo)
(Vuln)─[MENTIONED_IN]→(Paper)─[CITES]→(Paper)
(Product)─[EXPOSED_ON]→(Asset)
(Vuln)─[MAPS_TO]→(Technique)─[PART_OF]→(Tactic)
(Vuln)─[REGULATED_BY]→(Policy|Standard)
```

多跳查询用递归 CTE 实现（示例：查"依赖 vLLM 且有可用 POC 的漏洞"）：

```sql
WITH RECURSIVE reach(id, depth) AS (
    SELECT id, 0 FROM product WHERE lower(name) LIKE '%vllm%'
  UNION
    SELECT e.src_id, r.depth + 1
    FROM graph_edge e JOIN reach r ON e.dst_id = r.id
    WHERE e.rel IN ('AFFECTS', 'COMPONENT_OF') AND r.depth < 3
)
SELECT DISTINCT v.id FROM vuln v JOIN reach ON reach.id = v.id
JOIN poc p ON p.vuln_id = v.id;
```

## 6. 模块设计

### M1 数据采集 `services/collectors/`
- `CollectorRegistry` + `BaseCollector` 统一接口：`supports() -> bool`、`poll(watermark) -> list[RawItem]`。
- 4 个适配器：`NvdCollector`（CVE 5.1 API，关键词 AI/llm/vllm/ollama/…）、`GhsaCollector`（REST 轮询 + webhook 接收端实时入库）、`ArxivCollector`（API 关键词 cs.CR + LLM 安全）、`CommunityRssCollector`（RSS 解析 + 正文抽取）。
- 调度分级：webhook 实时 → 30 分钟轮询增量 → 每周全量；`sync_watermark` 记录游标与 etag，失败自动退避。
- 合规：固定 User-Agent、每源令牌桶限速、失败不重试风暴。

### M2 解析标准化 `services/ingest/`
- `trafilatura` 抽正文 → 截断到 6k 字符 → LLM 字段抽取（强制 JSON Schema）→ Pydantic 校验 → 落 `vuln`。
- CVE 字段对齐：`cve_id, title, description, cvss_*, cwe[], cpe[], published_at, modified_at, references[]`。

### M3 去重融合 `services/ingest/dedup.py`
- 精确：`content_hash`（正文归一化后 SHA-256）。
- 近似：SimHash 64 位 + 汉明距离 ≤3。
- 事件合并：同一 `cve_id` 的多条 `raw_item` 合并为一个 `vuln`，多源字段按可信度覆盖（CVSS 以 NVD 优先），保留全部证据链接 → 支撑"跨源交叉验证"叙事。

### M4 情报富化 `services/enrich/`

> **v1.1 更新**：维度由 4 扩到 **6 + 1**，对齐《SafeTrace 三件套》计划的 F1–F6，并保留已有的 AI 安全专项维度。
> 完整设计（接口、数据结构、降级、验收、成本重估）见 **`docs/富化线详细设计.md`**。

| 类别 | 维度 key | 说明 |
| --- | --- | --- |
| 计划 **6 大维度**（F1–F6） | `paper` `asset` `poc` `cvss` `fix` `consistency` | 对齐计划 F1–F6 |
| **AI 安全专项维度**（计划正文未列，本仓库已有且评分表需要） | `ai_risk` | AI 风险四级分类 + MITRE ATT&CK 映射；支撑"情报富化完整性"与"智能体架构"评分项 |

> 为什么不是刚好 6 个：`ai_risk` 是**已经跑通并有测试**的现有能力，且"AI 安全"是本赛题主题，
> 删掉它是纯粹的倒退。因此对外口径统一为「**6 维计划模块 + 1 个 AI 安全专项维度**」，
> 不假装成 6 个，也不把 ATT&CK 藏起来。

七个维度统一接口：`async def enrich(ctx, vuln) -> EnrichmentResult`，并行执行（`MAX_CONCURRENCY=4`）、
互不阻塞、失败单维降级（带 `degraded_to` 标记）。**每条结论必须带 `source` 与 `evidence`（URL + 原文片段 + 抓取时间）。**

| 维度 key | 计划模块 | 数据来源 | 方法 | 产出 | 现状 |
|---|---|---|---|---|---|
| `paper` 论文关联 | F1 | arXiv + Semantic Scholar | 双源检索 → LLM 三分类相关性判定 → 抽取方法与结论 | `vuln_paper` 关系 + 论文片段证据 | 已真跑（单源） |
| `asset` 受影响资产 | F2 | CPE + 版本区间（被动口径） | CPE 解析 + 厂商/产品归一 + 版本区间判定；组织资产画像走 Mock | 受影响产品/版本 + 暴露面 | 待补（默认 Mock） |
| `poc` POC 搜集 | F3 | GitHub + 公告 references + Nuclei 模板 | 三源检索 → 可信度分级 `confirmed/likely/mention` | `poc` 记录 + 可用性说明 | 已真跑（单源，`verified` 口径需修正） |
| `cvss` CVSS 与影响评估 | F4 | NVD 向量 + EPSS/KEV + 本地计算 | CVSS 3.1/4.0 向量本地计算（不靠 LLM 编分数）+ LLM 生成技术/业务影响与前置条件 | `cvss_vector/score` + 分层影响说明 | 已真跑（3.1） |
| `fix` 修复建议生成 | F5 | 公告 references（patch/advisory） | 参考文献分类 → 抽取修复版本与缓解项 → LLM 生成分级方案（立即缓解/升级/加固/检测） | 分级修复方案 + `patch_refs` | **待补（阻塞于 Y 线 `references` 入库）** |
| `consistency` 汇总与一致性校验 | F6 / D3 | 多源字段比对（计算为主，非 LLM） | 字段级一致性检查 + 冲突仲裁（NVD > 厂商 > GHSA > OSV > 社区）+ 质量分 | `consensus` / `conflicts` / `quality_score` / `timeline` | 待补（现有 `verify` 节点仅布尔检查） |
| `ai_risk` AI 风险分类 | —（专项） | 描述 + CPE | LLM 四级分类（AI 基础设施/推理框架 · 模型与数据层 · AI 应用与智能体 · 供应链）+ ATT&CK 编号白名单校验 | `ai_risk_category` + `ttp_mapping` | ✅ 已真跑 |

**证据链是核心设计**：每个字段都存 `evidence`（来源 URL + 原文片段 + 抓取时间），前端点开可溯源。
这直接支撑"富化准确率"与"推理链可解释"两个评分点。

**三条不变量**（写进测试，不允许绕过）：
1. `evidence` 为空的结果不落库（`indexer.py::_persist_enrichments` 已实现）；
2. `degraded_to != null` 时 `confidence ≤ 0.6`（降级结论不许包装成高置信）；
3. 修复版本号只能来自公告原文，LLM 编造的版本号必须丢弃。

**与知识底座的接口（当前缺口）**：`chunk` 目前只索引 `vuln.title + description + summary`，
富化结论**没有进检索空间**，导致 Q 线问"这个漏洞怎么修"召回不到 F5 结论。
需在 `indexer.py::persist_vuln` 中增加 `index_owner("enrichment", ...)`，把修复建议、一致性共识、影响说明编成 chunk 入向量库。

### M5 知识库与检索 `services/knowledge/`
- 写入：结构化表 + `chunk`/`embedding`（bge-m3 本地）+ `graph_edge` 关系边。
- 检索 `hybrid_search(query, k)`：
  1. 向量召回 Top-50（pgvector 余弦）；
  2. 关键词召回 Top-50（PG 全文 `tsvector` + trigram 模糊）；
  3. RRF 融合 → bge-reranker 重排 → Top-8。
- 支持 `owner_type` 过滤（只看漏洞 / 只看论文 / 只看标准）与时间过滤。

### M6 情报问答 `services/qa/`
- `QueryAgent` 流程：意图改写 → 查询扩展（3 个变体）→ 混合检索 → 关系边扩展（多跳线索） → 迭代检索（≤3 轮，依据"证据不足"信号再检索） → 生成（**强制引用 `[S1][S2]`**） → 自检（引用编号是否存在、结论是否被证据支持，不通过则重生成一次）。
- 回答结构：结论 → 依据（带可点击引用）→ 推理链（子问题与中间结论）→ 建议动作。
- 多轮对话：`session_id` 维护历史上下文（最近 3 轮原文 + 检索摘要）。

### M7 智能体编排 `agents/`
- 状态 `IntelState`：`{task, raw_items, vuln, enrichments, artifacts, budget(tokens/金额), retry_map, errors, trace}`。
- 主图 `build_monitor_graph()`：
  ```
  collect → normalize → dedup → triage ─(优先级)→ enrich(4维并行)
        → verify(证据校验) → persist(PG+向量+边表) → alert → report
  ```
- `Supervisor` 用条件边做路由：数据成熟度驱动（raw → merged → enriched），失败走 `repair` 分支（重试 → 换源 → 降级）。
- 所有节点统一装饰器：`@with_guard(timeout, retries, fallback)`。
- `WatchAgent`：周期健康检查（采集成功率、队列积压、模型时延、预算水位），触发自愈动作 + 告警 webhook。

### M8 平台服务与前端 `api/` + `web/`
- FastAPI：`/api/v1` 路由 + SSE 流式问答 + 简单 Token 鉴权 + 操作审计日志。
- 前端 3 页：态势大屏（趋势/分布/最新高危/延迟指标）、漏洞详情（富化字段 + 证据链展开 + 关系视图）、问答（流式 + 引用角标 + 历史）。

### M9 评测与可观测 `eval/` + `deploy/`
- 三个指标脚本 + 一个 100 条标注集（漏洞 30 / 富化 40 / 问答 30），指标结果直接进技术报告。
- Prometheus 指标：`intel_collect_latency_seconds`、`intel_enrich_success_ratio`、`intel_qa_latency_seconds`、`intel_llm_cost_cny_total`。

## 10. 成本治理（DeepSeek）

### 10.1 现行单价（2026-08-17 起峰谷分时计价，元 / 百万 tokens）

| 模型 | 时段 | 输入(缓存命中) | 输入(未命中) | 输出 |
|---|---|---|---|---|
| `deepseek-v4-flash` | 闲时（17h/天） | 0.05 | 1.5 | 4.5 |
| `deepseek-v4-flash` | 高峰（9-12、14-18） | 0.10 | 3.0 | 9.0 |
| `deepseek-v4-pro` | 闲时 | 0.15 | 4.5 | 13.5 |
| `deepseek-v4-pro` | 高峰 | 0.30 | 9.0 | 27.0 |

> 说明：旧的 `deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 下线，统一使用 `deepseek-v4-flash` / `deepseek-v4-pro`。价格随官方公告变动，充值前以 `api-docs.deepseek.com` 为准。

### 10.2 本项目 Token 预算（15 工作日 / 3 人 / 4 源 / ~1500 漏洞）

| 阶段 | 输入(M) | 输出(M) |
|---|---|---|
| 采集解析与字段抽取 | 7.5 | 0.9 |
| 富化 4 维 | 20.6 | 4.4 |
| 论文摘要与关联 | 4.5 | 0.6 |
| Agent 编排（Triage/路由/告警摘要） | 7.5 | 1.5 |
| 问答（评测 + 演示 + 试用） | 9.0 | 2.4 |
| 开发调试（含反复重跑） | 13.5 | 4.1 |
| 评测与报告生成 | 1.8 | 0.25 |
| **合计** | **64.4** | **14.1** |

成本模型（输入 40% 命中缓存，峰谷按 71% 闲时 / 29% 高峰加权）：

```
未命中输入 38.6M × 1.935 元/M ≈ 74.7 元
命中输入   25.8M × 0.065 元/M ≈  1.7 元
输出       14.1M × 5.805 元/M ≈ 81.9 元
                              ─────────
标准档合计                 ≈ 158 元（Flash 主力）
分级路由档（Pro 占 20%）   ≈ 220 元
全高峰 / 忘关思考模式      ≈ 450~600 元
```

**结论：充值 200 元可覆盖标准档 + 30% 余量；要用 Pro 分级就充 300 元；500 元封顶基本不会超。** Embedding/reranker 本地运行，API 成本为 0。

### 10.3 六条省钱铁律（写进代码规范）

1. **思考模式按需开启**：V4-Flash 默认开 thinking，思考 token 按输出计费，会放大 2~3 倍成本。字段抽取/分类/去重显式 `thinking=false`，只有富化推理、问答推理链用思考模式。
2. **前缀缓存优先**：system prompt + few-shot + 固定工具描述放在最前且保持稳定，命中价约为未命中的 1/30；重试同一 prompt 直接吃缓存。
3. **离线跑批钉在闲时**：富化回填、评测、报告生成等无人在等的任务用定时器钉在 0:00-9:00 / 12:00-14:00 / 18:00 后执行，输出价直接砍半。
4. **分级路由**：抽取/分类/去重 → Flash；富化解释、风险判定、问答推理链 → Pro。
5. **限制 max_tokens + 强制 JSON Schema**：输出是最贵的一项，砍掉超长思维链。
6. **预算闸门熔断**：`LLMRouter` 挂日配额（默认 20 元/天），超限自动切本地 Ollama 兜底并在日志/大屏标注"降级模式"——同时变成答辩自愈演示素材。

### 10.4 成本可观测

每次调用记录 `usage{input, cache_hit, output}` 与折算金额，落到 `data/cost.jsonl` 与 Prometheus 计数器 `intel_llm_cost_cny_total`，按 `agent/node/model` 打标签，可随时回答"钱花在哪了"。

### 14.4 三条工程红线（贯穿全周期，违反即一票否决）

1. **模型接入标准化解耦**：任何模型调用必须走 `core/llm.py` 的 `LLMRouter`（等价 MG1 网关），本地 vLLM/Ollama 与云 API 切换只改配置不改代码；`import` 任何 provider SDK 视为违规（可用 `tests/test_imports.py` 加一条断言固化）。
2. **脏数据不进知识底座**：每条情报过 Y 线 DQ1 质量闸门，不合格进隔离区，**宁可少一条，不可错一条**；F 线对 `quality_score < 0.4` 的条目拒绝富化。
3. **兜底必须显式可见，禁止静默兜底**：所有降级响应带 `degraded_to` 标记与用户可见提示，自愈动作全入 Trace。
