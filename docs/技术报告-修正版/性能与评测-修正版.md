## 一、口径说明（先看这一节，否则下面的数字会被误读）

三类数字，性质完全不同，**不能混在一起说"准确率"**：

| 类别 | 含义 | 可信度 |
| --- | --- | --- |
| **实测** | 本机真跑出来的指标，有原始产物 | 高（但样本小） |
| **回归基线** | 把当前产出固化成期望值，一致率必然 1.0 | 只能证明"没变"，**不能证明"对"** |
| **演示种子** | 由 `scripts/demo_seed.py` 构造的时间戳/数据 | 反映流程通，不代表真实采集能力 |

**样本量必须先声明**：本机演示库只有 **13 条真实漏洞、22 条原始情报、12 个知识切片**。
所有指标都建立在这个规模上，**不能外推到生产**。

## 二、问答模块实测（20 条黄金集，LLM-judge）

### 2.1 总览

| 指标 | 实测值 | 报告目标 | 达标 |
| --- | --- | --- | --- |
| 整体准确率 | **0.575** | ≥0.85 | ❌ |
| 响应 P95 | **95,891 ms ≈ 95.9 秒** | ≤5 秒 | ❌ |
| 引用率（答案带引用编号的比例） | **0.65** | >0.95 | ❌ |

### 2.2 按难度拆分

| 难度 | 题数 | 平均分 | 零分题 | 平均耗时 |
| --- | --- | --- | --- | --- |
| 单跳（single_hop） | 11 | 0.727 | 3 | 26.0 s |
| **多跳（multi_hop）** | 7 | **0.357** | 4 | **62.8 s** |
| 拒答（abstain） | 2 | 0.500 | 1 | 37.2 s |

### 2.3 客观分析（这些是真实短板，也是改进方向）

1. **多跳推理是真短板**：7 题中 4 题 0 分，平均 0.357，平均耗时 62.8 s
   （最慢 95.9 s）。原报告写"深度问答 ~78%"，是实测值的两倍以上。
2. **引用率 0.65**：20 题里 13 题 `citation_count = 0`——模型给了答案但**没挂引用**。
   "强制引用"是核心卖点，这里没做到。
3. **拒答不稳定**：问一个库里没有的云环境漏洞时没有拒答，反而引用了 8 条无关证据（得 0 分）；
   问一个不存在的 CVE 时正确拒答（得 1 分）。
4. **检索分数恒为 0**：所有 `citation.score = 0.0000`，因为本机没有嵌入模型
   （详见第四节"降级"）。

> **诚实的表述建议**：不要写"问答准确率 86%/78%"，写
> "在 13 条漏洞、12 个切片的小规模知识库上，20 题黄金集实测 0.575（单跳 0.727 / 多跳 0.357）"。
> 小样本 + 真实短板，比虚高的数字更经得起追问。

## 四、⚠️ 必须写进报告的降级说明（否则等于隐瞒）

本机环境的实际状态（全部实测）：

| 依赖 | 状态 | 后果 |
| --- | --- | --- |
| PostgreSQL | ✅ 16.15 运行中，库 `intel`，19 张表，迁移已到 `0002` | — |
| **pgvector 扩展** | ❌ **服务器上没有该扩展文件**（官方无 Windows 预编译包，需 MSVC 源码编译） | `chunk` 表**无 `embedding` 列** |
| **`sentence_transformers` / `torch`** | ❌ 未安装 | 嵌入、重排都无法计算 |
| → 检索方式 | **退化为 ILIKE 关键词匹配** | `citation.score` 恒为 0，多跳召回差 |
| Redis | ❌ 6379 无监听 | 事件总线走"已禁用"分支，事件被丢弃 |
| Docker | ⚠️ 已安装，**WSL2 组件启用后待重启** | `docker compose` 全栈尚未验证 |
| Ollama | ❌ 未安装 | 本地兜底模型未验证 |

**结论**：报告里**不能**写"混合检索（向量 + 全文 + RRF）已生效"、
"本地嵌入 BAAI/bge-m3（1024 维）"、"Embedding/Reranker 本地部署 0 API 成本"。
本机实测是**纯关键词检索**，向量那一路没有跑起来。

这符合项目自己的红线（"Mock/降级要说出口"），写清楚比藏起来更安全——
评委的常见追问就是"你这个向量检索用的什么模型"，答不上来比承认降级更糟。

## 九、本轮为"让指标能跑"修掉的 2 个 bug

这两个 bug 正是原报告数字无法产出、只能硬编码的直接原因：

1. **`QAAgent.answer()` 不接受 `stream` 参数**
   `eval/qa_accuracy.py` 调用 `agent.answer(q, stream=False)`，而 `answer` 把 `**kwargs`
   透传给 `answer_stream`（无 `stream` 参数）→ `TypeError`。
   **该指标此前从未跑通过。** 已在 `answer` 内显式吞掉 `stream`，
   并加 `tests/test_qa_answer_kwargs.py` 钉住。
2. **`collect_latency` 只读恒为 NULL 的 `latency_seconds`**
   `published_at`/`fetched_at` 都有真值却不用 → 报 `samples: 0`、`sla_tier: "fail"`。
   改为可由时间戳推导后：22 条样本、档位 `excellent`。已加 `tests/test_eval_collect.py`。

**教训**：报告里的数字必须是"跑出来的"，不是"写上去的"。
一旦某个指标从来没跑通，硬编码就会趁虚而入。
