## 1. 这是什么

「智能体驱动的 AI 安全知识情报系统」：多源采集 AI 漏洞情报 → LLM 富化多维度 → 向量入库 → 混合检索问答 + 态势大屏。

## 4. 已修的 bug（不要回退）

这些都是本轮实际踩到并修好的，改动相关代码时留意：

1. **QA 引用列表被数字覆盖**。`answer()` 先 yield 引用列表，`done` 事件又 yield 引用数量，前端拿到数字。现在 done 带 `citation_count`，引用列表单独走 `citation` 帧。
2. **SSE 帧格式非法**。`/qa/chat` 直接 yield Python dict，浏览器端 `data:` 后不是合法 JSON。改用 `dumps_event()` 输出 `data: {json}\n\n`。
3. **LangGraph 条件边 lambda 闭包**。循环里定义的 lambda 全部指向最后一个 `nxt`，所有分支都走错节点。必须用默认参数绑定（`lambda s, nxt=nxt: ...`）。
4. **`has_poc` 过滤破坏分页**。先分页再在 Python 里过滤，导致 `total` 与实际条数不一致。过滤已下推到 SQL。
5. **`DISTINCT ON` 崩溃**。`core/metrics.py` 里用了 PG 专有语法，SQLite 测试环境直接报错。改成 `count(distinct(...))`。
6. **富化评测三个错**。`_is_set_case` 不认 `true`/`false`；`_expected_positive` 判反；真负例（TN）没计入 `overall_accuracy`。
7. **水位线丢失**。`SyncWatermark` 加了 `last_sync_at`；`CollectorRegistry.poll` 现在持久化每源成功/失败、条数、最新发布时间、全量同步时间；单源失败隔离，写水位线失败不影响结果。
8. **Alembic 两个坑**。`0001_init.py` 必须**先 `CREATE EXTENSION vector` 再 `create_all()`**；`deploy/alembic/script.py.mako` 原本是空的，导致 `alembic revision` 生成的模板无效，已补齐。
9. **线程池里 `asyncio.create_task()`**。Starlette 的 `BackgroundTasks` 同步函数在线程池执行，直接 `create_task()` 会被拒（`no running event loop`）。已加 `api/deps.py` 的 `spawn()`。
10. **成本默认值不一致**。config 是 20，`.env.example` 写 70，README 写 1400。已统一为 `COST_DAILY_BUDGET_CNY=20.0`。

### P0 — `spawn()` 的线程安全仍有隐患
`api/deps.py` 的 `spawn()` 捕获了 loop，然后调 `loop.create_task()`。但调用方是 Starlette
的 sync BackgroundTask，**运行在线程池里**，跨线程调 `create_task()` 严格来说不安全
（文档要求 `call_soon_threadsafe` / `run_coroutine_threadsafe`）。测试能过是运气。
建议改：

```python
f = asyncio.run_coroutine_threadsafe(coro(), loop)
```

注意返回类型会从 `asyncio.Task` 变成 `concurrent.futures.Future`，检查有没有地方依赖 task 状态。

#### ⚠️ 这里踩过一个"提交密钥"的事故（务必看）

`config.py` 里备份原本写的是 `ENV_PATH.with_suffix(".env.bak")`。
`Path(".env")` 会被解析成"无 stem + 后缀 `.env`"，于是备份名变成 **`.env.env.bak`** ——
一个**不被 `.gitignore` 的 `.env` 规则覆盖**的新文件。
结果 `git add -A` 把含真实密钥的备份一起提交并推送了。

两层根因、两层修法，都别回退：

- **代码层**：不要用 `with_suffix` 处理"点开头的文件名"，改用字符串拼接
  （`ENV_PATH.parent / (ENV_PATH.name + ".bak")`）。
- **配置层**：`.gitignore` 用 **`.env*`** 整类挡掉，再显式放行 `!.env.example`。
  注意 **`.env.*` 这个 glob 匹配不到 `.env.env.bak`**（`*` 跨不过中间那个 `.`），
  所以必须是 `.env*`。另加 `*.log`（运行日志含本机路径与配置回显）。

教训通用化：**"不该入库的东西"要用"整类挡掉 + 白名单"的思路，
不要逐个列举**——列举一定会漏掉某个变体（备份、临时、带后缀）。

#### 另一个坑：PowerShell 脚本要加 UTF-8 BOM

`scripts/*.ps1` 里含中文。**没有 BOM** 时 PowerShell 5.1 按系统 ANSI 代码页（本机 GBK）
解码，中文被拆成乱码字节，个别字节组合被当成引号 →
报"字符串缺少终止符 / 意外的 `}`"这类**行列号与实际内容完全对不上**的假语法错误。
给 `.ps1` 加 UTF-8 BOM 后 0 错误。
**判断口诀：解析器报错位置对不上，先怀疑编码，别硬改语法。**
（仓库其它文件仍约定无 BOM，这个例外只针对 `.ps1`。）

## 7. 数据模型要点

- `vuln` 按 `cve_id` 唯一，多源数据挂在 `source_item` 上，靠它做关联。
- `chunk.embedding` 是 `vector(1024)`，HNSW 索引 `ix_chunk_embedding`。
- `chunk.tsv` 是 `tsvector` 生成列，配 GIN 索引做全文检索；`relation` 是自引用边表。
- `enrich_state` 状态机：`pending → enriching → repair / done / failed`，`repair` 是超时重试分支。
- `llm_usage` 每次调用记一条，`CostGuard` 按 `cost_date` 求和。
- `sync_watermark` 每数据源一行，记 `last_success_at` / `last_sync_at` / 条数 / 最新发布时间。

## 11. 给下一个 AI 的提醒

1. **可溯源性优先于准确率**。富化结论没证据就是 bug，别为了跑通评测而放宽。
2. **`POSTGRES_DSN` 指向 sqlite 时，PG 专有语法会炸**。`DISTINCT ON`、`pgvector` 运算符、
   `ON CONFLICT` 的 PG 变体都要避开，或加方言分支。`core/metrics.py` 已经踩过一次。
3. **新增 DB 逻辑先写测试**，用 `conftest.py` 的 fixture，不要因为"本机没 PG"就跳过。
4. **改富化维度列表**要同步 7 处（见第 1 节），最容易漏的是 `tests/test_imports.py` 的维度断言
   和 `core/contracts.py::DIMENSION_TO_CONTRACT`。
5. **`scripts/accept.py` 里的 `[SKIP]` 不是通过**。交付前要把能测的都变成 `[ OK ]`。
6. **不要引入 Neo4j / Elasticsearch / Celery**，是有意为之的设计决策，答辩会问理由。
7. README 里的性能数字（约 2 倍预算峰值）是实测得来的，改配置时同步更新，别写成理论值。
8. **降级必须显式**（`degraded_to`），**禁止静默兜底**；这是《SafeTrace 三件套》的三条工程红线之一。
9. **不要为了凑维度列表而删掉已跑通的能力**：`ai_risk`（AI 风险分类 + ATT&CK）计划正文没列，但它是赛题主题
   且已有真跑代码，属于"6 计划维度 + 1 专项维度"，删它是纯倒退。
   （融合后它还有了新身份：权威 6 值枚举之外的**扩展维度**，见 §0.3。）
10. **F 线做新功能前先读 `docs/富化线详细设计.md`**：它写明了每个维度的接口、降级口径、验收判据与
    需要 Y 线/S 线配合的字段，避免重复造轮子或改坏别人的线。
11. **★ 8 个权威 Schema 是冻结件，本仓无权改**。想加字段就加本仓扩展 Schema
    （照 `DimensionEvidence.json` 的做法），并更新 `scripts/validate_contracts.py::LOCAL_SCHEMAS`。
12. **★ 事件主题只能新增不能改语义**。新主题必须先在 `contracts/events.md` §3 登记，
    再加进 `EventEnvelope.json` 的 `topic` 枚举 —— 有个测试
    (`test_every_topic_is_declared_in_the_envelope_schema`) 强制这两处完全一致，
    漏一处就红。
13. **★ 不是 git 仓库**。改动前确认工作区状态，融合前备份见 §0.4。

1. **`source_ids` 与 `sources` 形状冲突**：权威 `source_ids` 是**源名字符串列表**
   （`["nvd","ghsa"]`），内部 `sources` 是**引用字典列表**（`asset.py` 读 `entry["url"]`）。
   直接互填会 `AttributeError: 'str' object has no attribute 'get'`。现在两者严格分开。
2. **`parse_nvd` 的 raw 包装约定**：只从 `raw` / `raw_json` 键取原始 CVE JSON。
   直接传裸 payload 会**静默返回空**（不报错，最难查的一类 bug）。
3. **`entities.version_range` 是 `string[]`**，内部 `version_ranges` 是带
   `introduced/fixed/source/url` 的字典。`to_intel_item` 现在压成 `"<=0.6.2"` 形式。
4. **两条降级不变量是跨字段约束，JSON Schema 表达不了**（`degraded_to` ⇒ 置信度上限、
   `degraded_to` ⇒ 必带原因）。它们由 `evidence.py::check_invariants` 在代码层强制，
   测试也针对它写，**不要试图把它们塞进 Schema 然后以为就管住了**。
5. **`confirmed` 置信度必须有可溯源 URL**。CPE 派生的 `version_range` 本身没有 URL，
   `fix.py::extract_target_version` 现在回退到 NVD 公告 URL —— 否则等于"没证据却声称确认"。
6. **`qa/agent.py` 的 `verdict` 只在 `else` 分支绑定**，无证据路径上引用会 `NameError`。
   现在初始化为 `{"passed": True, "score": 0.0}`（如实 0 分，对应 `Answer.abstained`）。
7. **降级事件载荷形状本来就是错的**，不只是主题名错。`fallback.events` 的权威内联契约是
   `FallbackEvent{layer, trigger, action_taken, degraded_of, user_visible, degraded_state}`,

   同样，`qa.queries` 是 `QueryTurn`，**耗时/成本不该塞进问句** —— 已移到 `qa.answers`。

### 14.14 向量落库：既有的 P-10 尾差落地（迁移 0004 + 维度守卫 + 幂等回填）（BigPickel · 2026-09-30）

#### 两条设计取舍（写进代码注释，便于日后调阈值）

1. **宁漏不误。** 本仓语料是安全公告与攻击技术论文，天然充满 `ignore`、

   而不是命中单个关键词。
2. **评分取最大权重，不求和。** 求和会让“命中 5 条轻微规则”盖过
   “命中 1 条决定性规则”，而后者才真正危险。

  该函数的设计是“**flag 优先于分数**”，先算 verdict 再补 flag 等于静默忽略
  （第一版就这么写的，被测试抓出来）。
- **QA**：`assess_injection_guard()` 由“恒 `screened=False`”改为**真筛**。
  语义要点：`screened` 表示“**做过**筛查”，不是“结果干净”——
  检出危险时仍为 `True`；没有引用时仍如实 `False`（没有输入就没有筛查动作）。

### 14.19 验证「富化到底有没有被问答用上」——挖出三个叠加真缺陷（BigPickel · 2026-10-01）

> 编号说明：本条原计划用 §14.18，但该编号已被并行 agent 的前端适配小节占用，
> 故顺延为 §14.19。

用户要求验证富化的问答效果。**结果发现这条链路实际是断的**，
而且缺陷全是静默的（不报错、只是能力不生效）。

#### 缺陷一：7 维富化只活下来 1 维

`index_owner()` 是"先删后写"（幂等设计），而 `persist_vuln` 的富化循环
**对每个维度都调它一次** → 每轮删掉上一轮 → **只剩最后一个维度**。

实测：`enrichment` 表 247 行，`enrichment` 切片只有 34 条、内容只剩 `ai_risk`
—— **问"这个漏洞怎么修"永远召回不到 `fix`**。

修法：`index_owner` 增 `replace` / `chunk_no_offset`（同一 owner 写多段时
只首段清空、之后追加并递增编号，否则各段 `chunk_no` 都从 0 开始会重叠）。
重建后 **94 条漏洞 / 583 条富化切片，缺口 0**。

#### 缺陷二：问某个 CVE 检不到它自己

两处叠加：
- `enrichment_chunk_text()` **不含漏洞身份**，产出纯结论（"修复建议：升级到 X"）
  → 按 CVE 编号提问时匹配不上，该漏洞的富化切片**永远进不了候选集**；
- `vuln` 切片正文也不含编号 —— NVD 的 `title` 就是英文描述截断。

修法：`enrichment_chunk_text(identity=…)` 把编号放**段首**
（切片有长度上限，放末尾会被截掉）；vuln 正文前置 `cve_id`。

实测 `CVE-2026-102697 怎么修复？`：
修前命中 `{'vuln': 8}`（引用全是别的 CVE）→ 修后 `{'vuln': 1, 'enrichment': 7}`，
S1/S2 都是该 CVE 自己。

#### 缺陷三：弱词淹没精确词

`_fallback_recall` 原实现 `WHERE ILIKE %t1% OR … OR %tn%` + `LIMIT top_k`，
把词的区分度拉平。实测查询 `CVE-2026-102697` 的分词命中数：

| 词 | 全库命中 |
| --- | --- |
| `2026` | **976** |
| `CVE` | 660 |
| `102697` | **2** ← 真正定位的 |

50 条限额被弱词占满 → 精确词永远进不来。改为**逐词单独查、按命中数升序**
（选择性高→低）取，精确词先占名额。

#### 缺陷四：自检节点再次被推理吃满

`qa.check` 的 `max_tokens` 从 `500` → `2500` 后**仍然被吃满**（`2500` 用尽、正文为空），
自检解析失败、`confidence` 退回按引用完整性判定。提到 `4000`。
注意 `judge` 既不在 `THINKING_TASKS` 也不在 `PRO_TASKS`（不开思维、走 flash 档），
但本仓模型连 flash 档也输出推理。

#### 一处**更正**：我先前的判断下重了

验证时看到 57 条漏洞共用同一条 `fix.immediate`，一度判为"演示库把富化数据串了"。
核对代码后**不是缺陷**：`fix.py` 开头即声明「**规则版真跑**…通用建议为模板」，
实测 `degraded_reason` 正是"F5 本轮为规则实现：版本号取自公告原文，通用建议为模板"。
**这是如实声明的规则兜底**。`base_score` 分布同样正常（7.5/8.8/7.8/7.1/9.8…）。

| 脚本 | 用途 |
| --- | --- |
| `scripts/verify_enrichment_used.py` | **验证富化是否真被问答引用**（本次四个缺陷都是它发现的） |
| `scripts/reindex_enrichment_chunks.py` | 重建富化切片（`--all` 强制重建残缺的） |

#### 教训

"补了富化" ≠ "富化被用上了"。**写入链路与读取链路要各验一遍** ——
这次是写入侧（切片互相删）与读取侧（编号不匹配、弱词淹没）**同时**出问题，
而两边都不报错。`scripts/verify_enrichment_used.py` 就是为此写的回归工具。
