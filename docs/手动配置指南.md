# 手动配置指南

目标：不依赖本机 Docker，本机跑通后端 + 数据库。本机（Windows）**必须手动装 PostgreSQL**——
项目自带的便携版 `embedded-postgres` 在 Windows 上 backend 进程会以 `0xC0000142`（DLL 初始化失败）崩溃，已验证不可用。

---

## 🚀 最快路径：SQLite 演示库 + 真实 LLM（本机实测，2026-09-29 夜）

不需要 PostgreSQL / Redis / Docker，5 分钟能起：

```powershell
cd E:\code\ai-threat-intel-demo-v1
$env:PYTHONPATH="$PWD\src"

# 1) 造演示库（SQLite；--db 必须显式传，否则会用默认 data/demo.db 覆盖你正在用的库）
C:\Python314\python.exe -m scripts.demo_seed --db data/demo.db

# 2) 配密钥：复制 .env.example 为 .env（.env 已被 .gitignore 忽略），填 LLM_API_KEY
#    然后起后端（uvicorn 会自动读 .env）
C:\Python314\python.exe -m uvicorn aiintel.api.main:app --host 127.0.0.1 --port 8000

# 3) 前端
cd web; npm install; npx vite --port 5180 --host
```

打开 <http://localhost:5180/>：导航栏显示「**实时数据**」= 已连上后端；
显示「预置数据」= 没连上，页面会写明回退原因（这是诚实降级，不是故障）。

> 若演示库是**旧版本**（例如模型加了列而库没加），不要整库重建，跑：
> `python -m scripts.sync_demo_schema.py`（只补缺列）
> 与 `python -m scripts.reseed_knowledge.py`（恢复知识库切片）。
> 两者都幂等、都不影响已有数据、服务在跑也能执行。

### ⚠️ 配 LLM 时的两个坑（都实际踩过）

1. **模型 ID 必须是服务端真实存在的名字。** 用
   `curl -H "Authorization: Bearer $KEY" https://api.deepseek.com/models` 查实际 id。
   本项目实测为 `deepseek-flash` 与 `deepseek-v4-pro`；
   曾误配 `deepseek-v4-flash`（不存在），配好 key 后 flash 档会被 400 顶回。

2. **`max_tokens` 给小了会导致"模型返回空字符串"。**
   本仓所用模型**强制输出思维链**，且思维 token 计入 `completion`。
   实测 `max_tokens=500` 时推理把额度吃满（`finish_reason=length`、`reasoning_tokens=500`、`content=""`），
   HTTP 仍是 200 —— 表现为"模型没报错，但什么都没返回"，规划与自检**每次都静默失败**。
   实测 2000 才留得下正文（reasoning≈1600 + content≈130）。当前取 2500（JSON 类）/ 3000（答案）。
   `LLMResult.truncated` 与 `LLMResult.reasoning_tokens` 可用来判断是否属于这种情况。

3. **本机没装 Ollama 时把 `LLM_LOCAL_ENABLED` 置 false**，否则云端失败后还会去连
   `localhost:11434` 白等一轮，把失败点拖后。

### 成本

问答一次（8 条证据、四段式答案）实测 **¥0.03 上下**，日预算 `COST_DAILY_BUDGET_CNY=20`。
每次调用的真实花费写在 `data/cost.jsonl`，页面上也显示单次成本。

## 0. 前置条件（完整路线：PostgreSQL + Redis）

| 软件 | 版本 | 说明 |
| --- | --- | --- |
| Python | 3.11 / 3.12 | 3.14 也测过，但 mypy 目标写的是 3.12 |
| Node.js | 20+ | 只在构建前端时需要 |
| PostgreSQL | 16 | 目标版本；17/18 兼容性未在项目上验证过 |
| Redis | 7 | 可选。缺失时事件总线降级，采集主链路仍能跑 |
| Ollama | 任意 | 可选。仅作 LLM 兜底 |

Docker 路线（推荐，一条命令）：`docker compose up -d postgres redis`，见 `docker-compose.yml`。

### Windows 上装 Docker 的两个坑（本机实测，2026-09-29 夜）

**坑 1：`wsl --install` 报「远程调用失败(403)」**

Windows 11 专业工作站版上实测：`Microsoft-Windows-Subsystem-Linux` 与
`VirtualMachinePlatform` 两个功能**已启用**（用 `Get-WindowsOptionalFeature` 复核过，
`dism` 那句"操作成功完成"是真的），但 `wsl --install` 与
`wsl --install --web-download` 都报 **403** —— 那是**下载**被拒（本机 GitHub API 也 403），
不是功能没开。**别在这上面反复重启**（本机为此白重启过一次）。

**坑 2：`winget install Microsoft.WSL` 会卡死**

实测两次都卡在 `winget` 里（CPU 0.4s、数分钟无下载进度），且卡在提权会话里、
普通权限 `Stop-Process` 杀不掉（要先提权）。

**可靠解法：直连 GitHub release 的 MSI**

```powershell
# 1) 下载（实测 247MB，GitHub CDN 约 4 秒；先确认版本号，见 releases/latest）
$url = 'https://github.com/microsoft/WSL/releases/download/2.7.14/wsl.2.7.14.0.x64.msi'
Invoke-WebRequest $url -OutFile wsl.msi -UseBasicParsing

# 2) 提权安装（静默）
msiexec /i wsl.msi /qn /norestart /l*v wsl-msiexec.log
```

成功判据（**不要只看命令没报错**）：

```powershell
Get-Service WslService      # 应从"不存在"变为 Running
wsl --version               # 应打印 WSL 版本 / 内核版本
```

本机实测结果：`WslService: Running`、`WSL 2.7.14.0`、内核 `6.18.33.2-2`、
`RebootPending = False`（**装完不需要重启**）。
之后重启 Docker Desktop，引擎即可就绪（实测 `ServerVersion 29.8.1`）。

一键脚本：`scripts/install-wsl-msi.ps1`（含下载、安装、复核三步）。

> 遗留：`scripts/fix-wsl*.ps1` 记录了三种**失败**尝试（`--web-download`、
> winget、单纯启用功能），保留仅为留痕，不要再用。

### ⚠️ 两个会浪费半天的环境陷阱（本机实测踩过）

#### 陷阱一：本机有**两个** PostgreSQL，`localhost:5432` 连到哪个要看 Docker 是否在跑

本机同时有原生 PG 服务与 compose 的 PG，两者都占 5432：

| 库 | 监听 | 关键差异 |
| --- | --- | --- |
| **原生 PG**（`postgresql-x64-16`，16.15） | `0.0.0.0:5432` | **无 `vector` 扩展**、`chunk` 表**无 `embedding` 列** |
| **compose PG**（`pgvector/pgvector:pg16`） | `[::]:5432` | **自带 `vector 0.8.6`**、`chunk` 表**有 `embedding` 列** |

Windows 上 `localhost` 会解析出 `::1`（IPv6，在前）与 `127.0.0.1`（IPv4）：

| 写法 | 连到 | 说明 |
| --- | --- | --- |
| `localhost:5432` | **运行 Docker 时**→ compose PG | `::1` 命中 Docker 发布的端口 |
| `127.0.0.1:5432` | **原生 PG** | IPv4，被 `postgres.exe` 占着 |

> ⚠️ **Docker 停掉之后两者都会落到原生 PG**（`::1` 上没人监听了）。
> 所以"`localhost` 连到哪个"**取决于 Docker 当时是否在运行** ——
> 这也是两个人测出不同结论的原因。别背结论，**用下面的方法当场判定**。

**当场判定连的是哪个库**（比记结论可靠）：

```sql
select current_database(),
       inet_server_addr(),                                             -- 172.x = 容器；空/127.0.0.1 = 原生
       (select count(*) from pg_extension where extname = 'vector');   -- 1 = compose PG；0 = 原生 PG
```

**踩过的后果**：我用 `127.0.0.1` 灌数据 → 进了**原生** PG；而 api 容器用服务名
`postgres` 连**容器** PG —— 两边表结构看着一样、`alembic_version` 却不同，
排查了两轮才定位。

**做法**：给 compose 的库灌数据时，**在容器内执行**（容器内 `postgres:5432` 无歧义）：

```powershell
docker cp data/demo.db safetrace-api-1:/app/data/demo.db
docker compose exec -T api python -m scripts.seed_from_demo --source data/demo.db
```

> **对语义检索的影响**（容易搞错）：`vector` 扩展**只缺在原生 PG 上**。
> compose PG 本来就有 pgvector，所以容器里不缺向量能力 ——
> 那边真正的阻塞是 **api 镜像没装 `sentence-transformers`+torch**
> （`deploy/Dockerfile` 的 `INSTALL_EMBED` 默认关，开启会让镜像 +约 10GB）
> 以及 **HF 权重取不到**（`huggingface.co` 不可达；`hf-mirror.com` 与
> `modelscope.cn` 可达）。这两条本仓已用 **ONNX 后端**绕开：
> 依赖约 15MB、权重走 hf-mirror，见 `services/knowledge/onnx_embedder.py`。

#### 陷阱二：npm 官方源可能不可达（构建 Web 镜像时）

实测容器内 `registry.npmjs.org` 连接超时（`npm error network ... behind a proxy`，
重试 782s 后失败），而 `registry.npmmirror.com` 可达。

仓库里**不写死**镜像源（能直连的环境用它反而更慢），改用构建参数按需覆盖：

```powershell
$env:NPM_REGISTRY='https://registry.npmmirror.com'; docker compose build web
```

同理，嵌入依赖（`sentence-transformers` + `torch` 约 2.5GB）默认不装：
本机 `huggingface.co` 不可达，装了也拿不到权重。需要时：

```powershell
$env:INSTALL_EMBED='1'; docker compose build api
```

> 容器可达性实测结论（2026-09-29 夜）：**可达** = PyPI / npm 镜像 / ModelScope /
> DeepSeek API；**不可达** = huggingface.co / hf-mirror / ollama registry /
> registry.npmjs.org。

## 1. 安装 PostgreSQL 16

winget install --id PostgreSQL.PostgreSQL.16

安装向导要填的东西（本项目要求）：

| 项 | 填什么 | 为什么 |

## 2. 安装 pgvector

**这是最关键的一步**，HNSW 索引和向量检索全靠它。忘了装会导致 `alembic upgrade` 在
`CREATE EXTENSION vector` 处失败。

### macOS
`brew install pgvector` 后执行 `ALTER EXTENSION vector UPDATE;`（或重启服务）。

### Debian / Ubuntu
```bash
sudo apt-get install -y postgresql-16-pgvector
```

### Windows（无官方包，两种方式）

**方式 A：pgAdmin 4 自带**（推荐，最省事）
打开 pgAdmin → 选 server → Tools → **Extension Manager** → 搜 `vector` → Install。

**方式 B：手工放文件**
1. 从 https://github.com/pgvector/pgvector/releases 下载 v0.8.x 的 zip。
2. 解压后把 `vector.control` 和 `vector--*.sql`、`vector.dll` 按位置放好：
   - `vector.control` → `C:\Program Files\PostgreSQL\16\share\extension\`
   - `vector--*.sql` → 同上目录
   - `vector.dll` → `C:\Program Files\PostgreSQL\16\lib\`
3. 重启服务：
   ```powershell
   Restart-Service postgresql-x64-16
   ```

> `vector.dll` 必须是和你的 PostgreSQL **同架构（x64）**且用兼容编译器（MSVC）构建的，
> 否则 `CREATE EXTENSION vector` 会报 `could not access file "$libdir/vector.dll"`。

### macOS 手工方式
```bash
git clone --branch v0.8.6 https://github.com/pgvector/pgvector.git /tmp/pgvector
cd /tmp/pgvector && make && sudo make install
sudo psql -c "CREATE EXTENSION vector;"
```

### 验证
```bash
psql -d postgres -c "SELECT default_version FROM pg_available_extensions WHERE name='vector';"
# 应输出 0.8.6 之类
```

## 3. 建库建用户

### Windows（psql 在 PATH 里通常找不到，用全路径）

```powershell
$env:PATH = "C:\Program Files\PostgreSQL\16\bin;$env:PATH"
psql -U postgres -c "CREATE ROLE intel LOGIN PASSWORD 'intel_dev';"
psql -U postgres -c "CREATE DATABASE intel OWNER intel;"
psql -U intel -d intel -c "CREATE EXTENSION vector;"   # 必须 intel 是 superuser 或 vector 已 install 到该库
```

> `CREATE EXTENSION` 需要在 `intel` 库里执行，**不能只在 `postgres` 库里建**。

如果报权限不足，把 `intel` 临时提为 superuser，建完扩展再降级：
```powershell
psql -U postgres -c "ALTER ROLE intel SUPERUSER;"
```

### macOS / Linux
```bash
sudo -u postgres psql -c "CREATE ROLE intel LOGIN PASSWORD 'intel_dev';"
sudo -u postgres psql -c "CREATE DATABASE intel OWNER intel;"
sudo -u postgres psql -d intel -c "CREATE EXTENSION vector;"
```

## 8. Redis（可选）

不需要 Redis 也能跑——事件总线会降级、告警功能失效，但采集和问答正常。
需要时：

```bash
docker run -d -p 6379:6379 redis:7-alpine
# 或 Windows 上装 Memurai / 用 WSL
```

然后 `.env` 里设 `REDIS_URL=redis://127.0.0.1:6379/0`。

> Redis 是**可选**的：没起 Redis 系统照常跑，只是事件发不出去。
> 但请保留默认的 `REDIS_SOCKET_TIMEOUT_SECONDS=0.5`——没有它，Redis 不可用时
> 每条事件要等约 4 秒才放弃，一轮富化十几条事件会把主链路拖慢近一分钟。

## 故障排查速查

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `could not access file "$libdir/vector.dll"` | pgvector 没装或架构不匹配 | 回第 2 步 |
| `extension "vector" is not available` | `CREATE EXTENSION` 在错的库里执行 | 在 `intel` 库里建 |
| `type "vector" does not exist` | 没建扩展就迁移 | 先 `CREATE EXTENSION vector;` |
| `could not translate host name` | Postgres 没在跑 | Windows: `Get-Service postgresql-*` |
| `connection refused 127.0.0.1:5432` | 端口不对 / 没监听 | 检查 `postgresql.conf` 的 `port` 和 `listen_addresses` |
| `SSL connection error` | DSN 没写 `sslmode` | 拼成 `postgresql+psycopg://...` 通常即可 |
| `permission denied for schema public` | 库不是 intel 建的 | `ALTER DATABASE intel OWNER TO intel;` |
| `extension "vector" must be installed in schema` | 装到别的 schema | `ALTER EXTENSION vector SET SCHEMA public;` |
