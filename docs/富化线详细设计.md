## 2. 富化线统一契约（所有维度共用）

每个维度是**纯函数 + 显式输入输出**，禁止跨维度直接调用，禁止在维度里写库。

维度清单（4 → 7）：

| # | key | 计划模块 | 本轮动作 |
| --- | --- | --- | --- |
| 1 | `paper` | F1 | 补第二源与章节级证据 |
| 2 | `asset` | F2 / D2 | **新增**（CPE 解析为主，资产画像 Mock） |
| 3 | `poc` | F3 | 补多源 + 可信度分级（修正 `verified` 口径） |
| 4 | `cvss` | F4 | 补 CVSS 4.0 / EPSS / KEV / 三层影响 |
| 5 | `fix` | F5 | **新增**（本轮重点） |
| 6 | `consistency` | F6 / D3 | **新增**（可信度叙事核心） |
| 7 | `ai_risk` | —（专项，计划正文未列） | **保留不动**：AI 风险四级分类 + MITRE ATT&CK 映射，已有真跑代码与测试，且是赛题主题 |

> **为什么是 6+1 而不是 6**：计划附录总图的 F 线只画了 F1–F6，但计划第一篇的赛题对应表与评分表都要求
> "AI 风险分类 / ATT&CK 映射"这类 AI 安全专有能力，且本仓库已有可运行实现。
> 因此对外口径统一为「**6 维计划模块 + 1 个 AI 安全专项维度**」，既不删已有能力，也不虚构第 7 个计划模块。

```python
# services/enrich/dimensions.py
async def dimension_fn(vuln: dict) -> EnrichmentResult
```

### 2.1 输入：IntelItem（Y 线出口，F 线只读）

F 线**不直接读 `raw_item` 表**（除非做证据回溯），输入统一为下面的字典。字段来自 `Vuln` + `VulnSource`。

| 字段 | 类型 | 来源 | F 线用途 | 现状 |
| --- | --- | --- | --- | --- |
| `id` | str | `vuln.id` | 富化归属、关系边 | ✅ |
| `cve_id` / `ghsa_id` / `aliases` | str / str / list | `vuln` | 跨源匹配、检索键 | ✅ / ✅ / ❌ 需 Y 线补 |
| `title` / `description` / `summary` | str | `vuln` | LLM 提示词语料 | ✅ |
| `cvss_vector` / `cvss_score` / `severity` | str / float / str | `vuln` | F4 复算与冲突比对 | ✅ |
| `cwe` / `cpe` | list[str] | `vuln` | F2 资产解析、F4 影响面 | ✅ |
| `affected_products` | list[str] | 归一阶段（**未入库**） | F1/F2/F3 检索关键词 | ⚠️ 需 Y 线入库（见 §7 待办 1） |
| `references` | list[dict] | 归一阶段（**未入库**） | F3 POC、F5 补丁链接 | ⚠️ 需 Y 线入库（阻塞 F5） |
| `published_at` / `modified_at` / `fetched_at` | ISO str | `vuln` / `raw_item` | F6 时间线、证据 `fetched_at` | ✅ |
| `sources` | list[{source, url, external_id, published_at}] | `vuln_source` + `raw_item` | **每条结论的 `source` 与交叉验证** | ⚠️ 需新增读取函数（见 §6.1） |
| `quality_score` | float 0–1 | Y 线 DQ1 | 低于阈值只做低置信富化 | ❌ 需 Y 线补（见 §6.1） |
| `version_ranges` | list[{product, introduced, fixed}] | OSV / 厂商公告 | F2 受影响版本、F5 修复版本 | ❌ 需 Y 线补（阻塞 F5 的准确性） |

### 2.2 输出：EnrichmentResult（F 线出口，S 线入口）

```jsonc
{
  "dimension": "paper|asset|poc|cvss|fix|consistency|ai_risk",
  "value": { ... },                       // 见各维度章节
  "source": ["arxiv", "nvd", "github"],   // ★ 本次结论实际依据的数据源（赛题硬要求）
  "evidence": [                           // ★ 可溯源证据链，至少 1 条
    {"source": "arxiv", "url": "https://arxiv.org/abs/2609.01234",
     "snippet": "原文片段（≤600 字）", "fetched_at": "2026-09-28T10:00:00+00:00"}
  ],
  "confidence": 0.0,                      // 0–1
  "model": "deepseek-v4-flash",
  "agent": "EnrichAgent",
  "version": 1,
  "created_at": "ISO8601",
  "degraded_to": null,                    // ★ FB1：null | "cache" | "local" | "mock" | "rule"
  "degraded_reason": "",                  // ★ 人话说明，前端与日报直接展示
  "note": ""
}
```

**三条不变量**（写成测试，不允许绕过）：

1. `evidence` 非空才能落库（`indexer.py::_persist_enrichments` 已实现，保持）；
2. `evidence[].url` 必须与 `value` 中出现的 URL 一致，或为 `value` 结论的直接来源页（F6 校验）；
3. `degraded_to != null` 时，`confidence` 必须 ≤ 0.6（降级结论不许包装成高置信）。

### 2.3 并行执行与超时（保持现状）

`services/enrich/agent.py`：`MAX_CONCURRENCY = 4`、`TIMEOUT_PER_DIMENSION = 180s`、单维异常转 `error` 字段不阻断其他维度。
维度数由 4 增至 7 时**不需要改这里**（`DIMENSIONS` 字典即注册表），只需重估并发与成本（见 §5.4）。

## 3. F1–F6 详细设计

### F1 论文关联（`paper`）

| 项 | 设计 |
| --- | --- |
| 目标 | 从 arXiv + Semantic Scholar 找出与漏洞同源/同攻击面/提供检测与缓解方法的论文，产出关系与结论 |
| 接口 | `async def paper_association(vuln: dict) -> EnrichmentResult` |
| 数据源 | arXiv Atom API（已接，`services/collectors/arxiv.py::_parse_atom` 复用）；Semantic Scholar Graph API `paper/search`（新增） |
| 步骤 | ① 构造检索式：`cve_id` 优先，退化到 `affected_products` + 攻击面关键词；② 双源检索去重（按 DOI / arXiv ID）；③ **章节级证据抽取**：取摘要 + 命中章节原文段落（不是整篇塞进 LLM）；④ LLM 三分类判定 `same_vuln` / `same_attack_surface` / `method_for`；⑤ 抽取论文给出的关键结论（≤3 条，每条必须能回指原文片段） |
| `value` | `{"papers": [{"paper_id", "arxiv_id", "doi", "title", "year", "url", "relation_type", "relevance", "confidence", "findings": ["..."], "snippet_ref": "ev-1"}]}` |
| 落库 | `paper` 行 + `vuln_paper`（`relation_type` / `note`）+ `graph_edge(MENTIONED_IN, paper)` |
| 降级 | arXiv 挂了→只走 Semantic Scholar；两者都挂→`degraded_to="rule"`，只回关键词命中榜（`confidence ≤ 0.3`） |
| 置信度 | 命中且有原文片段 0.7；命中但仅元数据 0.45；无命中 0.3 且 `papers=[]` |
| 验收 | 抽检 20 条关联，≥80% 人工认可；100% 结论附论文 URL + 摘要片段 |
| 测试 | `tests/test_enrich_paper.py`：fake `_get_text` 返回固定 Atom → 断言只看 relevant 条目、断言 evidence 非空、断言双源去重不重复收录同一 DOI |

### F2 受影响资产（`asset`）— 默认 Mock + 合规门

| 项 | 设计 |
| --- | --- |
| 目标 | 把 CPE / 版本区间翻译成"受影响产品与版本范围"，并与组织资产画像对比给出暴露面 |
| 合规红线 | **不主动扫描、不探测、不利用**。资产画像只能来自：用户导入清单、公开可授权数据（被动指纹）；`asset_scan_enabled` 默认 `false`，开启需显式配置并在报告标注 |
| 接口 | `async def asset_impact(vuln: dict) -> EnrichmentResult` |
| 步骤（真跑部分） | CPE 解析（`cpe:2.3:a:vendor:product:version:...`）→ 厂商/产品归一（`aliases` 归一）→ 版本区间判定（用 Y 线 `version_ranges`，缺失时标注"版本范围未知"） |
| 步骤（Mock 部分） | 组织资产清单 → 产出 `exposed_assets: []`，值来自 `data/assets.sample.json`，`degraded_to="mock"`，前端显示「预置数据」徽标 |
| `value` | `{"products": [{"vendor", "product", "cpe", "affected_versions": ">=0.5.0,<0.6.2", "range_source": "osv\|vendor\|unknown"}], "exposed_assets": [], "exposure_level": "none\|low\|medium\|high", "mock": true}` |
| 降级 | 无 CPE → `degraded_to="rule"`，只回 `affected_products` 文本匹配结果，`exposure_level="unknown"` |
| 验收 | 20 条抽检产品/版本解析正确率 ≥85%；Mock 数据在 UI 与报告均显式标注 |
| 红线检查 | `tests/test_enrich_asset.py::test_no_active_probe`：断言模块不发起除白名单域名外的出站请求，且 `settings.asset_scan_enabled=False` 时 `exposed_assets` 恒为空 |

### F3 POC 搜集（`poc`）

| 项 | 设计 |
| --- | --- |
| 目标 | 找出可复现的验证代码 / Nuclei 模板 / 利用情报，给出**可信度分级**而不是"有/无" |
| 数据源 | ① GitHub `search/repositories`（已接）+ `search/code`（需 `GITHUB_TOKEN`，无 token 退化为只搜仓库）；② 咨询/公告 `references` 链接（ExploitDB、厂商通告、安全博客）；③ Nuclei 模板（`projectdiscovery/nuclei-templates` 仓库内按 CVE 号检索） |
| 分级规则 | `confirmed`：模板命中或仓库含 CVE 号 + 可运行入口文件 + star ≥ 5；`likely`：仓库描述/README 命中 CVE 号；`mention`：仅在 issue/博客中被提及 |
| `value` | `{"pocs": [{"repo", "url", "kind": "exploit\|patch\|template\|analysis", "language", "stars", "tier": "confirmed\|likely\|mention", "evidence_kind": "code\|template\|writeup", "runtime_verified": false, "usage"}]}` |
| **重要口径修正** | 现有代码把 `verified` 写死 `true`（`dimensions.py:184`）——这是"看起来像造假"的隐患。改为：`listed`（已被检索到）/ `tier`（可信度分级）/ `runtime_verified`（**是否真的跑过**，初赛恒 `false`，标注"未运行"）。**绝不允许把"检索到"写成"已验证"** |
| 降级 | GitHub 限流（403/429）→ `degraded_to="cache"`，读本地 `data/poc_cache.json`；无 token 且限流 → `tier` 全部降一级 |
| 落库 | `poc` 表（`kind`/`language`/`stars`/`verified` 保持，`verified` 语义 = tier ≥ likely）+ `graph_edge(HAS_POC, repo)` |
| 验收 | 有 POC 的漏洞中，`tier=confirmed` 的抽检 20 条 ≥90% 属实；UI 不出现"已验证"字样（除非 `runtime_verified=true`） |

### F4 CVSS 与影响评估（`cvss`）

| 项 | 设计 |
| --- | --- |
| 目标 | 分数**本地计算**（可复核），影响面由 LLM 解释（可溯源），补充 EPSS/KEV 做优先级 |
| 计算 | 扩展 `services/enrich/cvss.py`：保留 CVSS 3.1 完整实现（已验证），新增 CVSS 4.0 向量解析（`CVSS:4.0/AV:...`，按官方 MacroVector 简化实现，返回值 + `score_source="computed"`）；向量不可解析时**不猜分数**，`score=null`、`score_source="unavailable"` 并写 `note` |
| 情报补齐 | 从 NVD 2.0 `cve.metrics` 与 `cisaExploitAdd` 取 `epss` / `kev`（Y 线已抓 `raw_json`，F 线按 `raw_json` 读取，避免重复请求） |
| LLM 部分 | 三层影响说明：`technical_impact`（技术影响，≤100 字）、`business_impact`（业务影响）、`affected_scenarios[]`（受影响场景）、`prerequisites`（前置条件）。**LLM 不得输出分数/版本号**，提示词显式禁止，输出后正则校验含数字分数字段则丢弃该字段 |
| `value` | `{"vector", "base_score", "severity", "qualitative", "score_source": "computed\|vendor\|unavailable", "epss", "kev", "technical_impact", "business_impact", "affected_scenarios", "prerequisites", "computed_locally": true}` |
| 证据 | NVD 详情 URL + 原文描述片段（保持现有）；有厂商公告时追加其 URL 与版本段落 |
| 降级 | LLM 失败→仍返回本地分数（`degraded_to="rule"`，`confidence=0.6`）；向量缺失→`confidence ≤ 0.4` |
| 与 F6 的关系 | F4 给出"我们的分数"，F6 负责与 NVD/GHSA/厂商分数比对并仲裁冲突 |

### F5 修复建议生成（`fix`）— 新增，本轮重点

| 项 | 设计 |
| --- | --- |
| 目标 | 回答"现在该怎么修"，并且**每个版本号都能追到来源** |
| 输入依赖 | `references[]`（Y 线需入库）、`version_ranges[]`（Y 线需入库）、F3 中的 `kind=patch` 命中 |
| 步骤 | ① 参考文献分类：`patch`（commit/PR/发布说明）、`advisory`（厂商/CNVD/GHSA 公告）、`exploit`、`other`；② 从 patch/advisory 中抽取修复版本、缓解配置项、临时规避手段；③ LLM 生成分级修复方案：`immediate`（今日可做的缓解/隔离）、`upgrade`（升到哪个版本，必须来自 ①，缺失则写"待确认"）、`hardening`（配置加固）、`detection`（怎么发现是否已被利用）；④ 冲突检查交给 F6 |
| `value` | `{"immediate": [{"action", "rationale", "evidence_ref"}], "upgrade": {"target_version": "0.6.2", "source": "vendor", "url": "..."}, "hardening": [...], "detection": [...], "patch_refs": [{"url", "kind", "provider"}], "version_confidence": "confirmed\|inferred\|unknown"}` |
| 硬规则 | **版本号只能来自 patch/advisory 原文**；LLM 输出的版本号必须在 ① 抽到的文本里出现，否则丢弃并置 `version_confidence="unknown"`（写进测试） |
| 降级 | 无 patch 参考 → `degraded_to="rule"`，只给通用缓解建议（`confidence ≤ 0.4`），并显式写"未找到官方补丁" |
| 验收 | 有官方补丁的 CVE（≥15 条）中，升版本号正确率 ≥90%；无补丁的必须诚实输出"未找到"而不是编造 |

### F6 汇总与一致性校验（`consistency`）— 新增，富化线的"可信度"叙事核心

| 项 | 设计 |
| --- | --- |
| 目标 | 把多源情报放在一起比对：一致的给共识值，冲突的显式暴露，全程保留证据来源；产出可展示的**数据质量分** |
| 实现 | `services/enrich/consistency.py`：字段级比对，**主要是计算而非 LLM**（便宜、可复现） |
| 比对字段 | `cve_id` 别名、`cvss_score`（容差 ±0.1）、`severity`、`affected_products`、`fixed_version`、`exploit_status`、`published_at`（时区/日期级差异只告警不判冲突） |
| 冲突判据 | 数值型：差异 > 容差且两者都有来源 → `conflict`；枚举型：不同值 → `conflict`；集合型：一方为另一方子集 → `partial` |
| 仲裁策略 | 优先级 `NVD > 厂商公告 > GHSA > OSV > 社区`（可配置 `ENRICH_SOURCE_PRIORITY`）；共识值取最高优先级来源的值，并在 `arbitration` 里写明"谁被否掉、为什么" |
| `value` | `{"consensus": [{"field", "value", "source", "agreement": 0.67, "sources": ["nvd","ghsa"]}], "conflicts": [{"field", "values": [{"value","source","url"}], "resolved_to", "rule"}], "quality_score": 0.83, "source_coverage": {"nvd": true, "ghsa": true, "vendor": false}, "trace_refs": ["ev-1","ev-2"]}` |
| 质量分公式 | `quality_score = 0.4*字段完整率 + 0.3*多源一致率 + 0.3*证据覆盖率`（三项都可从 DB 直接算，公式写进文档与评测脚本） |
| 落库 | `enrichment(dimension="consistency")` + `graph_edge(CONFLICTS_WITH, conflict:<field>)`（前端可点开看冲突双方） |
| 降级 | 单源（只有 NVD）→ 不产 `conflicts`，`quality_score` 上限 0.6，`degraded_to="rule"`；LLM 仅用于把冲突写成一句人话（`degraded_to="local"` 时退回模板句） |
| 验收 | 构造 20 条已知冲突样例（NVD 9.8 vs 厂商 8.1 等），检出率 ≥90%、误报率 ≤10%；被仲裁掉的来源在 UI 可见 |

## 5. 横切设计

### 5.1 证据链溯源（赛题硬要求，最高优先级）

**目标**：任取一条富化结论，能一键看到「原始 URL + 原文片段 + 抓取时间 + 模型 + 版本」。

链路（现状 + 待补）：

```
raw_item(url, content_text, fetched_at)          ← Y 线采集，已落库
   │ vuln_source(vuln_id, raw_item_id, source)   ← 已落库 ✅
   ▼
Enrichment(dimension, value, evidence[], confidence, model, version)   ← F 线落库 ✅
   │ （本轮补）每条 evidence 增加 source 字段与 trace_ref 自增编号
   ▼
GET /vulns/{id}/evidence → 前端"查看证据"展开（已有 UI）✅
   │ （本轮补）证据链上溯到 raw_item 原文（点击 evidence.url 打不开时回落到 raw_item 存档正文）
   ▼
GET /agents/runs/{id} → 每一步的输入摘要/输出摘要/成本 ✅
```

待补两项：
1. `services/enrich/evidence.py`（新建）：统一的 `evid(source, url, snippet, fetched_at)` 构造器 + `attach_sources(field_name, sources)` 标注"这条结论依据了哪些源"，替代当前散落的 `_evidence()`。
2. `GET /vulns/{id}/evidence` 响应增加 `sources`、`quality_score`、`degraded_to` 三个字段（向后兼容，前端可选读）。

### 5.2 降级可见（FB1，三条工程红线之一）

| 层级 | 触发 | 行为 | `degraded_to` |
| --- | --- | --- | --- |
| L1 重试等幂 | 单次网络失败 | 指数退避重试 ≤3（`BaseCollector` 已有；富化维度加 `tenacity` 包装） | `null`（不算降级） |
| L2 容器/依赖自愈 | 向量库/Redis 不可用 | 跳过索引与事件，主链路继续 | `null`（记录 warning） |
| L3 降级服务 | 数据源不可达 / LLM 超时 / 预算耗尽 | 用缓存、fixture、规则或本地模型 | `"cache"` / `"fixture"` / `"rule"` / `"local"` |
| L4 熔断 | 日预算耗尽、连续失败超阈值 | 停止云调用，切本地，前端与日报打「降级模式」 | `"local"` / `"mock"` |

**落点**：
- `core/llm.py::LLMResult.degraded`（已有）→ 富化维度把它转成 `degraded_to="local"`；
- `core/metrics.py` 增加 `intel_enrich_degraded_total{dimension, degraded_to}`（新增计数器）；
- `GET /metrics/overview` 的 `enrich` 段增加 `degraded_ratio` 与 `per_dimension{confidence_avg, coverage, degraded_ratio}`；
- 日报（`agents/report.py`）增加一行"今日降级次数与原因 TOP3"。

**禁止静默兜底**：任何返回 `degraded_to != null` 的结论必须在 `note` 里写明原因（写进测试断言）。

### 5.3 质量闸门协同（DQ1）

F 线消费 Y 线的 `quality_score`，不重复实现闸门：

| quality_score | F 线行为 |
| --- | --- |
| ≥0.7 | 全量 7 维富化 |
| 0.4–0.7 | 只做 F4/F5（成本低、价值高），F1/F3 跳过并记 `note` |
| <0.4 | 不富化，状态置 `pending` 并在隔离区可见（Y 线负责隔离，F 线负责"不浪费钱"） |

> 当前 `enrich_state` 状态机（`pending → enriching → repair/done/failed`）保持不变；**新增 `skipped_low_quality` 状态**需同步 `db/models.py` 与前端展示。

### 5.4 成本控制（7 维后的重估）

| 维度 | LLM 调用量/漏洞 | 任务档 | 备注 |
| --- | --- | --- | --- |
| F1 paper | 3–5 次 classify | flash（关思考） | 与现状相同，只多一个检索源（不计 LLM） |
| F2 asset | 0 | — | 纯解析 + Mock |
| F3 poc | 3–5 次 classify | flash | 现状相同 |
| F4 cvss | 1 次 enrich | pro（开思考） | 现状相同，最贵的一项 |
| F5 fix | 1 次 enrich | pro | **新增成本**，建议 `max_tokens=900`，只在有 patch 参考时开思考 |
| F6 consistency | 0–1 次 reason | pro 或纯规则 | 单源时 0 调用 |
| `ai_risk` | 1 次 classify | flash | 现状不变 |

结论：维度 4→7，**LLM 调用量约 +40%**，但 F2/F6 主要是计算。策略：
① F5/F6 排在 F1/F3 之后（`DIMENSIONS` 有序，`EnrichAgent` 已是 `gather` 并发，成本闸门用 `CostGuard.exceeded()` 动态降级）；
② 回填（backfill）钉在闲时（0:00–9:00 等），单位成本砍半；
③ `COST_DAILY_BUDGET_CNY=20` 不变，超限走本地 Ollama，富化结果标 `degraded_to="local"`。

### 10.1 维度定义表（对外口径，与 `dimensions.py` 一致）

| key | 中文名 | 计划模块 | 数据来源 | 是否 Mock |
| --- | --- | --- | --- | --- |

| `poc` | POC 搜集 | F3 | GitHub + references + Nuclei 模板 | 否 |

| `fix` | 修复建议生成 | F5 | patch/advisory references + LLM 组织 | 否（无补丁时诚实输出） |

### 10.2 一次富化的完整数据轨迹（答辩演示脚本）

```
POST /collect/sync                       # Y 线：采集 → 去重 → IntelItem
  └─ IntelItem(vuln_id=v_xxx, sources=[nvd, ghsa], references=[...], quality_score=0.82)
       └─ EnrichAgent.run(vuln)          # F 线：7 维并发
            ├─ paper       → evidence(arxiv.org/abs/...)        confidence 0.70
            ├─ asset       → degraded_to="mock"                 confidence 0.50
            ├─ poc         → tier="confirmed" ×2                confidence 0.80
            ├─ cvss        → base_score=9.8 (computed) + EPSS   confidence 0.90
            ├─ fix         → upgrade 0.6.2 (vendor advisory)    confidence 0.85
            ├─ consistency → conflict: nvd 9.8 vs vendor 8.1
            │                 resolved_to=9.8 rule=NVD优先        quality_score 0.83
            └─ ai_risk     → category=ai_infrastructure          confidence 0.75
                             techniques=[T1190]
       └─ persist_vuln ↓
            ├─ enrichment ×7（每条带 source/degraded_to/evidence）
            ├─ graph_edge: HAS_POC / MENTIONED_IN / FIXED_BY / CONFLICTS_WITH / MAPS_TO
            └─ chunk(enrichment) → 向量库（Q 线可检索"怎么修"）
GET /vulns/v_xxx/evidence                # 前端展开证据链，逐条核对原文
```

### 10.3 与计划文档的差异声明（必须写进技术报告「已知限制」）
