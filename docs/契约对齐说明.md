# 契约对齐说明（Python 演示侧 → 上游 TS 仓）

> 面向团队：说明 `ai-threat-intel-demo-v1`（KKK9747human 的 Python 演示应用）
> 如何跟随上游 `contracts/schemas`。**本文件不宣称与之合并**——两仓结构不同，
> 只做**契约逐字同步 + 语义对齐**。

## 一、为什么不是"合并"

| 项 | upstream（团队 TS 仓） | demo-v1（Python 应用） |
| --- | --- | --- |
| 语言 | TypeScript（单体仓） | Python + Vue |
| 顶层 | `src/`、`contracts/`、`web/` | `src/aiintel/`、`web/`、`eval/` |
| Python 文件 | **1 个**（`scripts/validate_contracts.py`） | 全部 |
| 共享内容 | `contracts/schemas/*.json`（权威 8 个） | 同上，逐字同步 |

两仓无共同祖先，**不存在直接合并**。可共享的只有权威契约，做法是逐字复制 + 指纹冻结。

## 二、同步现状：已达 v1.1.3

`contracts/schemas/FROZEN_MANIFEST.json` 记录 8 个权威 schema 的 sha256；
`scripts/validate_contracts.py` 校验字节一致，并支持
`SAFETRACE_CONTRACTS_DIR=<上游路径>` 做**跨仓交叉核对**。

本轮跟随 C-01~C-04 同步过程：

| 步骤 | 结果 |
| --- | --- |
| 交叉核对（v1.0.0 时） | 8/8 一致 |
| 上游升至 v1.1.3 后 | **6/8 仍逐字一致**，2 个有差异（C-01 `DecisionReply`、C-02 `RetrievalResponse`） |
| 差异性质校验 | **纯追加**：`+human` 枚举值、`+published_at`、`+trust`；**0 删除、0 值改变、required 未动** |
| 同步后交叉核对 | **8/8 逐字一致** |

> 校验方式：把两份 schema 扁平化成键集比较，任何"删除 / required 变更"都直接拒绝，
> 避免把破坏性变更当兼容更新吞进来。

## 三、C-02 落地：`trust` / `published_at` 不只是改了 schema

只同步 schema 不改代码 = 字段永远为空，用户仍不知道证据是否权威。Python 侧已全链路落地：

| 层 | 文件 | 做法 |
| --- | --- | --- |
| 分级口径 | `src/aiintel/services/knowledge/trust.py` | 与上游 `sourceTrust()` **逐条对齐**：`nvd`/`cve_org`/`ghsa`/`osv`/`kev`/`arxiv` = trusted；`community_rss`/`vendor_advisory`/`security_blog`/`poec_source`/`github_search` = untrusted |
| 推导 | `services/knowledge/retrieval.py::_source_meta_map` | `published_at` ← `Vuln.published_at`；`trust` ← 该漏洞 `VulnSource.source` 集合合成 |
| 透出 | `services/qa/agent.py` | 引用事件带两字段；**有才放**（缺省不塞 None） |
| 展示 | `web/src/views/QaView.vue` | 「权威源 / 外部文本 / **未评估**」+「发布时间 / **未知**」 |

**一处刻意的语义选择，请团队确认是否与 TS 侧一致**：
`combine_trust()` 在"权威源 + 社区源混合"时判 **trusted**（有一个权威源即 trusted）。
理由是权威记录已确认该条目，社区转载只影响增量信息。上游 `sourceTrust()` 是**逐源**判定，
合并语义在 TS 侧由谁负责需要对齐。

另一个刻意选择：**认不出的来源返回 `None`（未知），不返回 `untrusted`**。
契约把缺省定义为"未知"，硬说成 untrusted 同样失真（会无端降低证据可信度）。

## 四、C-04 落地：时效与注入筛查

上游 q4-answer.ts 的口径已在 Python 侧独立实现
（`src/aiintel/services/qa/freshness.py`，未照搬代码，语义对齐）：

| 字段 | 本仓实现 | 与上游一致性 |
| --- | --- | --- |
| `stale_warning.threshold_days` | 默认 **365** | 同上游 `DEFAULT_STALE_THRESHOLD_DAYS` |
| 判定依据 | 取**最早**一条的年龄 | 同上（最旧证据决定结论多可能过时） |
| 部分未知 | 只要有一条缺 `published_at` 就提示并报条数 | 同上 |
| 全部未知 | 单独给更重的措辞 | 同上 |
| `injection_guard.screened` | **恒为 False** | 同上游（A-04 未落地前必须显式 false） |
| `injection_guard.untrusted_evidence` | 统计 `trust=untrusted` 条数 | 同上 |

**未实现（有意）**：`injection_score` / `injection_flags` 的**检测**。
上游同样只落了契约位并注明"检测实现归 A-04"，本仓不超前实现。
`InjectionFlag` 的十类枚举已抄录在契约里，A-04 落地时两边可对齐同一套分类。

## 五、两处**主动不采用**的上游做法（附理由）

1. **Qdrant**：本仓栈是 PostgreSQL，且本机 PG 装不上 `vector` 扩展
   （官方无 Windows 预编译包）。引入 Qdrant 只为一件事（语义检索），
   却要新增一个服务与一条数据路径，性价比不划算 —— 先用 PG 全文 + 应用层 RRF。
2. **`hashVector` 特征哈希向量**：上游自己在代码里写明
   「仅供兼容性测试；**不得写入语义 Qdrant 集合**」。本仓**同样拒绝**用它冒充语义检索
   —— 那等于把"哈希碰撞的相似"说成"语义相似"。本仓当前如实降级为关键词检索，
   并在响应里标明 `citation.score = 0` 是"词法兜底排序"。
